# 故障型錄：六種在這套系統裡反覆出現的故障型

原系統把出過的故障整理成型錄，每一型都要答三件事：怎麼認出它、怎麼掃到它、怎麼修它。新的事故先查有沒有同型的。這裡只放純工程、不帶任何一件具體事故的六型，每一型寫它在這個倉庫裡對應的示範。

## 1. 假綠燈

- **怎麼認：** 狀態頁全綠，但用起來慢、怪、或結果不對。服務活著不代表它走的是該走的路。
- **怎麼掃：** 每一個「OK」旁邊都要有「走的是哪一條路」：退路有沒有被走到、走了幾次。沒有這個欄位的燈，不算燈。
- **怎麼修：** 退路必須計數、必須露在健康檢查上；啟動順序要寫成「前一層健康檢查通過才起下一層」，不是「起了就算」。
- **倉庫裡：** `reliability/failover.py` 的 `problems()` 會把「備援＝主力」這種假備援先報出來；`verification/daily_checkup.py` 把 fallback 當一條規則數。

## 2. 「有在跑」不等於「有做到」

- **怎麼認：** 一批修改全部通過檢查，但問「每一項的最終目標達到了沒」答不出來。
- **怎麼掃：** 每一項修改動手前先寫三欄：最終目標（使用者感受得到的一句話）、量什麼、過關線。缺一欄就亮紅。
- **怎麼修：** 驗收分兩層記：程式有照寫的跑，跟目標有沒有達到。只有前一層的，不准標「好了」，標「觀察期」或「只確認程式有在跑」。
- **倉庫裡：** `verification/closure_check.py` 的 R4；`docs/adr/003-two-layer-acceptance.md`。

## 3. 尺量到外殼

- **怎麼認：** 埠活著就當服務正常；檔案存在就當內容是對的；流程跑完就當結果是對的；審查員有回報就當它看過了。
- **怎麼掃：** 訂每一把尺的時候問一句：它量的是容器還是裡面的東西？
- **怎麼修：** 尺要碰到內容。服務要讀它的健康檢查欄位，檔案要比對內容，審查員要先餵它已知的錯。
- **倉庫裡：** `verification/canary.py` 用兩個分數量審查員，不用「它有回報」；`verification/sandbox_guard.py` 的金絲雀先證明守門真的會擋，才開始信它。

## 4. 靜默退回

- **怎麼認：** 失敗時填一個看起來正常的預設值往下送；退回慢速路徑只印一行 INFO；超過長度的部分直接丟掉、不記。
- **怎麼掃：** 找程式裡所有「失敗就用預設值」「超過就截斷」的分支，看它有沒有計數、有沒有露出。
- **怎麼修：** 失敗就是失敗，明講；退回要計數、要露在健康檢查；截斷改成退回另一條路並記次數。
- **倉庫裡：** `reliability/fail_loud.py`（反例：填了預設值之後，壞掉的回答跟真的「中性」一模一樣）；`retrieval/router.py` 失敗時退回規則，不是退回「全部不查」。

## 5. 驗證器自己驗自己

- **怎麼認：** 驗證結果寫死「通過」；審查員從來沒被考過；測試只檢查函式有沒有被呼叫，不檢查它做了什麼；兩個來源相近的說法互相同意就當成驗證。
- **怎麼掃：** 餵驗證器一個已知的錯，看它會不會過。會過，它就不是驗證器。
- **怎麼修：** 先考審查員（故意埋錯），再用它的話；測試量行為，不量呼叫；重要判斷走兩條彼此獨立的路。
- **倉庫裡：** `verification/canary.py`；這個倉庫每個做法的測試都附一個「拿掉這個做法會怎樣」的反例，證明測試量的是行為。

## 6. 紅慣了的燈

- **怎麼認：** 每天的報告都有同樣十一個紅燈，第十二個新的混在裡面，沒人看見。
- **怎麼掃：** 報告跟昨天的自己比：新的、變嚴重的排最上面；已知的另列。
- **怎麼修：** 已知問題登記在清單，修好就拿掉；再犯會自己浮回最上面。報告唯讀，不叫模型、不碰資料。
- **倉庫裡：** `verification/daily_checkup.py`（反例：沒有已知清單、照次數排，新問題在最後一行）。
